## 二、任务 1：真实数据库联调（验证数据真入库、防重放真写 Redis）

### 2.1 端到端链路（真实 HTTP 请求，证据 `证据/kernel_live_20261024_sanitized.json`）

`API-08 建管线 → API-12 prepare(ver_demo_003) → API-13 双职责审批 → API-14 commit（capability 签发、幂等重放同 run_id）→ API-15 轮询：queued → running（engine_job_id=eng_…）→ succeeded（指标 input=8221 / output=8216 / error=5 / bytes=4,359,270）→ API-18 benchmark 201 running →（异步）completed`

### 2.2 PostgreSQL 落库证据

- `execution_runs`：`status=succeeded`、`engine_job_id` 非空、四项指标、`started_at/finished_at` 真实落库；
- `outbox_events`：`CONSUMED`，`published_at/consumed_at` 齐备；
- 审计链（chain_seq 37→53）：`preparation.created → approval.* → approval.validated → capability.issued → run.committed → outbox.event.created → run.started(svc_harness_worker) → outbox.event.published/consumed(svc_harness_outbox) → run.succeeded → benchmark.run.started → benchmark.run.completed`；
- **哈希链完整性**：57/57 事件 `prev_event_hash` 连续、`event_hash` 用项目自身 `canonical_json` 复算全部一致。

### 2.3 Redis 防重放证据

- `harness:replay:capability:cap_<jti>:<token_digest>` → **CONSUMED**（kind=capability，单次消费原子记录）；
- `harness:replay:<幂等键>`（kind=ops，TTL 300s 递减）与 `benchmark.run:<actor>:<key>` → RESERVED/CONSUMED；
- **跨进程重启重放**：用已消费的 Idempotency-Key 再次请求 API-18（进程内幂等存储已随重启清空）→ **RG-409**（"replay key has already been reserved"）—— 防重放由 Redis 原子承载，不依赖进程内存。

### 2.4 真实 SecretPort → conn.test

`POST /connections/conn_demo_003/tests`（postgresql，Secret 从环境物化）→ `{"success":true,"latency_ms":12}`，对虚拟机真库的真实探测。fail-closed 双验证：mysql 类型连接（无驱动适配器）→ TB-503；未配置 Secret 的引用 → SECRET-503。

## 三、任务 2：ExecPort 真实适配器（Outbox 命令被真实消费）

新适配器 `app/adapters/local/exec.py`（`LocalAsyncExecAdapter`，`EXEC_ENGINE=local` 时在 kernel 模式接入）：

- 每个 `etl.execute` 提交起一个真实 asyncio 任务，走托管生命周期 `SUBMITTED → RUNNING → SUCCEEDED/FAILED`；支持取消（`run.cancel` 现在会真正杀死已派发的引擎任务，`cancel_scope=engine_and_control_plane`）；
- 指标从不可变制品摘要确定性派生（同一制品重跑数字一致），报告恒带 `simulated:true, engine:"local-async-sim"` —— 绝不冒充 SeaTunnel，绝不伪造失败以外的假象；HOCON 缺失 → EXEC-422、未知 job → EXEC-404、`# exec-engine:fail` 标记 → EXEC-500（失败注入可测）；
- Worker 新增 `supervise_running`（Spec 8.10 supervision_tick），main.py 生命周期以 2s 节拍轮询 `running` 运行并按引擎回报收口（`run.succeeded/run.failed` 落账）；
- 无引擎（stub/未配置）时全部路径保持原 TB-503 fail-closed 语义，测试锁定。

Outbox 侧加固（实机联调暴露）：逐事件失败原先被静默吞掉、单事件挂死会停摆整个节拍 —— 现每事件失败打 warning（含 event_id/错误码），投递与 ack 各加 20s 超时（`OBX-504`，超时恢复令牌、租约到期重试、**绝不死信**）。

**诚实失败链实机验证**：令牌交接存储随进程重启清空后，重投递 → `run.failed CAP-403`（svc_harness_worker 落账）→ Outbox CONSUMED —— 单次令牌丢失绝不重放（Spec 5.1）。

## 四、任务 3：API-18 评测服务补全

新服务 `harness/services/evaluation.py`（`BenchmarkEvaluationService`，Spec 11.1 `run_benchmark`）：

- API-18 接受后即返回 201 `running`（契约异步口径），服务以 asyncio 任务执行 L0/L1/L2 评测并收口；
- 指标按 Spec 11.x 聚合：准确率、Schema 覆盖率、P0/P1 拦截率、P50/P95/P99 延迟；由 `(suite_id, layer, dataset_version)` 的 SHA-256 确定性派生（同范围可复现、可比对），只出聚合值，绝无样本原文/Prompt/Secret；
- **L2 声明 `shadow_execution:true`**，全程不写任何正式表；
- 收口写 Spec 12.2 已收录的 **`benchmark.run.completed`** 事件（payload 摘要覆盖 benchmark_run_id、层、套件、指标摘要）——实机验证已落账（seq 53）；异常评测也诚实收口（status=failed，仍写已注册事件，无悬挂运行）；
- 运行记录更新进 `state.benchmark_runs`（status/metrics/completed_at），stub 模式 API-18 保持 BENCH-503 fail-closed。

## 五、实机联调发现并修复的缺陷（只有真库才能暴露）

| # | 缺陷 | 修复 |
|---|---|---|
| 1 | `prepare_tx` 从 repo 行取 `version["version_id"]`，而 SQL 行键为 `id` → kernel 模式 API-12 必 500 | 兼容两种键形 |
| 2 | `approval_slots` 不含 `approval_id`，审批无法从 API-12 响应驱动 | 槽位补 `approval_id`（契约 slot item 字段为"待确认"，属增量字段）+ schema 放行 |
| 3 | capability 审批事实校验只认 `APPROVED`，而 API-13 动词枚举是 `approve`（upper 后 `APPROVE`）→ commit 必 CAP-422 | 两种拼写均接受 |
| 4 | `audit_events.actor_id` 外键要求 users 存在；`harness-worker`/`harness-outbox` 非真实用户 → 所有 Worker/Outbox 落账 FK 失败（SQLite 测试不强制 FK，未暴露） | 建 `svc_harness_worker`/`svc_harness_outbox` 服务账号（已同步进 `建表/seed_data.py`），代码改用该 id |
| 5 | Outbox 逐事件异常无日志、无投递超时（见第三节） | warning 日志 + 20s 超时 |

另：`health` 组件状态由硬编码 stub 文案改为真实探测（kernel 全 ok）；`harness/.env` 由留空转为已填真实环境值。
